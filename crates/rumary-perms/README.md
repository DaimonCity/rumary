# rumary-perms

Проверка прав в стиле LuckPerms для `rumary-api`: wildcard-ноды, контексты,
наследование групп, веса ролей, временные права — плюс resource-level ACL
поверх того же хранилища.

Доменные типы живут в `rumary-dto` (`domain::perms`), здесь — только логика.

## Три независимые проверки

Их легко перепутать, но они отвечают на разные вопросы, и для действий над
другим пользователем нужны ВСЕ:

| Что | Вопрос | Тип |
|---|---|---|
| RBAC | может ли роль вообще делать такое (`configuration.delete`) | `PermissionService` |
| ACL | открыт ли доступ к ЭТОЙ записи (`configuration` с таким id) | `ResourceAcl` |
| Ранг | выше ли actor, чем цель действия | `require_outranks` |

Право `profile.delete` без проверки ранга позволило бы manager-у удалить
admin-а. Право `configuration.get` без ACL открыло бы все чужие конфигурации.

## Структура

- `resolver.rs` — чистая функция резолвинга: wildcard-матчинг + приоритеты
- `store.rs` — трейт `PermissionStore` (чтение) + `InMemoryStore`/`FailingStore`
- `admin.rs` — трейт `PermissionAdmin` (запись: группы, ноды, членство)
- `service.rs` — `PermissionService`: кэш + `check` / `require` / `try_resolve`
- `hierarchy.rs` — сравнение ранга по максимальному весу роли
- `resource_acl.rs` — ACL поверх таблицы `resource_access`

## Использование

```rust
// где-то в состоянии приложения:
let perms = PermissionService::from_arc(store, Duration::from_secs(60));

// внутри бизнес-логики — отказ прокидывается через `?`:
perms.require(user_id, &key, &ctx).await?;   // PermissionResult<()>

// или как bool, когда отказ — ветка логики, а не ошибка:
if perms.check(user_id, &key, &ctx).await { ... }
```

`key` — `PermissionKey` из `rumary-dto`, а не `&str`: невалидные ключи вида
`api.ord*` или `api..read` отсекаются при разборе, а не молча не совпадают
никогда.

`PermissionService` — `Clone` (внутри `Arc`), кладите его в `AppState`.

## Порядок разрешения конфликтов

1. Специфичность: точная нода > `api.orders.*` > `api.*` > `*`. Точный сегмент
   даёт +10, wildcard +1 — поэтому узкий грант всегда перебивает широкий, а не
   выигрывает по случайности порядка строк.
2. Приоритет источника: прямая нода пользователя (`SourcePriority::USER`) >
   группа с большим весом > группа с меньшим.
3. При полном равенстве побеждает **Deny** — детерминированно и fail-closed.

Нет совпадений — `Tristate::Undefined`. Это не то же, что Deny: политику
"Undefined значит запретить" применяет вызывающий код (`as_bool(false)`).

## Fail-closed и ошибки хранилища

`check` при недоступности БД возвращает `false` — запрещает. `require`
возвращает `StoreError`, чтобы хендлер ответил 500, а не 403: сбой БД не
должен выглядеть как отказ в правах.

Ошибка загрузки НЕ кэшируется — иначе секундный сбой запретил бы всё на весь
TTL кэша.

## Инвалидация кэша

После записи через `PermissionAdmin` кэш устаревает:

- изменили права/группы пользователя — `invalidate_user(user_id)`;
- изменили права ГРУППЫ — `invalidate_all()`: заранее неизвестно, кто входит
  в неё через наследование.

Без явного вызова изменение вступит в силу по истечении TTL.

## Что реализовать под свою БД

`PermissionStore::load_effective_nodes` должен вернуть уже "развёрнутый"
список нод — прямые ноды пользователя плюс ноды всех групп с учётом
наследования, с выставленным `source_priority`. Резолвинг wildcard, контекста
и TTL сервис берёт на себя.

Реализация поверх Postgres — в `rumary-api/src/repo/perms.rs`. `role_snapshot`
там переопределён, чтобы роли и ранг брались одним запросом вместо двух
проходов по одному и тому же рекурсивному CTE.

## Пример

```
cargo run -p rumary-perms --example usage
```

Кастомная роль writer, явный Deny поверх группового wildcard, контексты и
проверка ранга — без БД, на `InMemoryStore`.
